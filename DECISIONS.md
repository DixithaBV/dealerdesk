## 1. Schema (models, relationships, `on_delete`)
- `catalog/models.py:4` **Product**: unique `sku`, `price` DecimalField(12,2) with a CHECK `price > 0`.
- `catalog/models.py:23` **Inventory**: **OneToOne → Product, `CASCADE`** (line 25). Stock has no meaning without its product. One row per product is the row that is locked (`SELECT … FOR UPDATE`) when stock changes. CHECK `quantity >= 0` is a database-level backstop against overselling.
- `catalog/models.py:33` **InventoryAdjustment**: FK → Product `CASCADE` (line 34); an audit trail of manual stock PUTs that goes with the product.
- `catalog/models.py:41` **Dealer**: unique `dealer_code`.
- `orders/models.py:6` **Order**: FK → Dealer **`PROTECT`** (line 11): a dealer who has orders must never be deletable (financial records). `stock_deducted` guards "restore stock exactly once".
- `orders/models.py:24` **OrderItem**: FK → Order `CASCADE` (line 25; items are part of the order) and FK → Product **`PROTECT`** (line 26; a product on an order cannot disappear). UNIQUE(order, product) mirrors the "no duplicate SKU" rule; CHECK `quantity >= 1`.
- `orders/models.py:41` **OrderSequence** (one row per IST day) and `orders/models.py:50` **IdempotencyRecord** (unique key + request hash; FK → Order `CASCADE`, nullable until the order exists).
- `assistant/models.py:4` **ChatMessage**: `session_id` is a plain string, **no FK**, on purpose: sessions are anonymous and must never share memory, so history is looked up by `session_id` only (`assistant/engine.py:34`).

## 2. How retrieval works, why, and where it fails
Hybrid and deterministic, no embeddings (`assistant/retrieval.py`). The catalogue is templated (`<Part> - <Vehicle>`, 600 rows, 11 categories), so the hard problem is *fitment*, not semantics, and dense vectors blur "Duke 200" and "Duke 390". A free embedding API would also add latency, quota risk and run-to-run variance when the grader runs the assistant three times.
1. **Vehicle resolution** (`resolve_vehicle`, line 63): the query, or the model's `vehicle` argument, is matched against the known fitment strings by model tokens. One match = resolved; several = `ambiguous` (line 113), and the tool tells the model to ask (`assistant/tools.py:77`); none = unknown.
2. **Part scoring** (`search`, line 97): IDF-weighted overlap (`idf`, line 56) on part name + category + brand tokens, with plural stemming, a small synonym map (`tire→tyre`, `lamp→headlight`, …) and typo repair via `difflib` (`_correct`, line 87).
3. **Hard compatibility filter** (line 136): only `fitment == resolved vehicle` or `Universal` can be returned. If the part type is vehicle-specific and no vehicle was given, `needs_vehicle=True` (line 140) and nothing specific is returned, so the model asks the dealer.
Ties are broken by SKU, so repeated runs return identical results.
**Where it fails:** words outside the synonym list (e.g. "stopper"); vehicle spellings the token match cannot resolve ("yzf"); two part types in one sentence (only the best-covered type is returned); a bare number such as "150". With more time I would add a dense re-ranker *behind* the same hard fitment filter, and a labelled evaluation set.

## 3. The tool-calling loop (user message → reply)
`ChatView.post` (`assistant/views.py:25`) validates input and calls `run_turn` (`assistant/engine.py:49`):
1. Load this `session_id`'s last 16 messages (`engine.py:34`, `HISTORY` line 14) and append the user message (line 54). A per-request budget of 50 s (`TURN_BUDGET_SECONDS`, line 15) keeps us under the contract's 60 s.
2. `llm.generate(...)` (`engine.py:59`) is `GeminiClient.generate` (`assistant/llm.py:44`): a POST to Gemini `generateContent` with the three `functionDeclarations`, temperature 0 and the lowest "thinking" level (`THINKING_OPTIONS`, line 13). An overloaded model (5xx, line 71) or retired one (404, line 78) fails over to the next candidate model.
3. If the response contains `functionCall` parts they are executed against the **real database** by `tools.execute` (`engine.py:65` → `assistant/tools.py:156`), recorded for `tool_calls` (line 64) and returned as `functionResponse` parts (line 66); the loop repeats, at most 6 steps (`MAX_STEPS`, line 13). The raw model content, including any `thoughtSignature`, is sent back unchanged.
4. When the model answers in text, `guard.check_reply` verifies it (`engine.py:71`; see Q4). The first failure sends the model an automated correction message (lines 75-82); a second failure replaces the reply with a deterministic one built only from tool results (`_fallback`, line 42, used at line 83).
5. `LLMError` (line 87) returns a short apology instead of an error. Then `cited_skus` is computed from SKU codes in the reply that exist in the DB (line 92) and both messages are stored (lines 93-94).
`create_draft_order` (`tools.py:122`) calls the same `orders.services.create_order` as `POST /api/orders/` (`tools.py:130`) with an idempotency key built from (session, turn, items), so a model that repeats the call still creates one order. `dealer_id` comes from the request, never from the model.

## 4. Prices and stock: how the reply is kept truthful
Nothing is cached or remembered between turns. Prices and quantities come only from tool calls made in the **current** request: `search_parts` (`tools.py:69`), `check_stock` (`tools.py:90`) and `create_draft_order` (`tools.py:122`); the system prompt (`engine.py:17-30`) tells the model to call the tools again each time rather than reuse earlier figures. Every tool records the figures it exposed in `Turn.prices / quantities / skus` (`tools.py:30`). Before a reply is released, `assistant/guard.py:30 check_reply` extracts every ₹ amount (`MONEY_RE`, line 7), every "N units / in stock / available" number (`QTY_RE`, line 8) and every SKU code, and rejects the reply if an amount or quantity is not in this turn's tool facts (a multiple of a known price is allowed for totals), a SKU does not exist, the reply is not in the dealer's language, or it ignores the parts the tools returned. `search_parts` deliberately returns only `in_stock: true/false` (`tools.py:72`), never a count, so any quantity in a reply must have come from `check_stock`.
**Limit:** the guard recognises figures that sit next to a currency symbol or quantity word; a number written in an unusual way ("one thirty-six pieces") would not be caught.

## 5. Untrusted catalogue text and where the defence stops
1. **Descriptions are not shown to the model raw.** `clean_text` (`assistant/sanitize.py:14`) keeps only the harmless leading sentences and cuts everything from the first sentence that matches an injection pattern (`_INJECTION`, line 5; cut at lines 21-22): "ignore previous…", "NOTE FOR AI ASSISTANTS", `[system]`, "admin mode", "% off", "code", "without checking…". It is applied at `tools.py:72` and capped at 140 characters. Both injected rows in `data/catalogue.csv` are cut (tested in `tests/test_pure_assistant.py`).
2. Tool results carry a notice that catalogue text is data (`tools.py:17`), and the system prompt (`engine.py:17-30`) forbids following it and forbids mentioning discounts or codes.
3. **Structural:** the model can only call three whitelisted tools (`tools.py:156`); `create_draft_order` can only create a DRAFT for the request's dealer; nothing can confirm an order. An injection cannot reach a destructive action.
4. **Output guard:** discount/coupon claims and `VIKMO-…` codes are blocked (`guard.py:10`).
**Where it stops:** the sanitiser is a pattern list. A paraphrased injection that avoids every pattern would reach the model; layers 2-4 then limit the damage to misleading *text*, which the guard only partly catches (it checks numbers, SKUs and promo words, not general falsehoods). Product *names* and brands are passed through unfiltered.

## 6. Forecasting approach, validation, and the leakage guard
`ml/forecast_pipeline.py` (scikit-learn only; LightGBM was avoided to keep the grader's install light and the run reproducible).
- **Model:** one global `HistGradientBoostingRegressor` (3 seeds averaged, `fit_predict`, line 149) over all 40 SKUs, **direct** strategy for horizons 1-4. The target is `log1p(units)` minus the SKU's own trailing level (`REL_TARGET`, line 30; `_level`, line 143), so the model learns *shape* (promotions, Diwali) rather than scale. Features (`feature_row`, line 74): lags 1-4, 4/8/13/26-week means, volatility, zero-fraction, same week last year, the target week's promo flag, trailing promo rate, signed weeks to the Diwali week, week of year and category. `MIN_HIST = 3` (line 29) lets the 2024 Diwali ramp contribute training rows.
- **Promotions:** the promo flag of the *target* week is a feature; it is known in advance, and the history shows roughly a 2.2× lift. **Diwali:** `weeks_to_diwali` (line 53) uses the nearest Diwali date from `festival_calendar.csv`, so the 2026 ramp is placed relative to 8 Nov rather than last year's calendar week (same-week-last-year is off by about 2.5 weeks).
- **Leakage guard:** `train_rows` (`ml/forecast_pipeline.py:137-139`) keeps only rows whose **target week ≤ the cutoff**. Every row's features are built from `y.loc[:origin]` only (`build_rows`, line 115; `forecast_components`, line 194). The backtest (line 247) and the final fit (line 281) use the same `forecast_components` function (line 187), which trains with `train_rows` at line 191.
- **Validation:** rolling-origin backtest at 7 cutoffs (2025-09-15 … 2026-08-24, `cutoffs`, line 243), 4-week horizon, 40 SKUs, retrained at each cutoff. Result (`ml/backtest_report.json`): MAE **9.41** vs 11.19 for the best baseline (4-week average) = **15.9% better**; RMSE 14.84 vs 18.68; WAPE 0.254 vs 0.302. Other baselines: last value MAE 13.91; same-week-last-year 12.20. Variants tried on the same backtest (min-history / target): 8 absolute 9.60, 8 relative 9.62, 3 absolute 9.49, 3 relative 9.41 (chosen).
- **Honest caveats:** the blend weight (0 / 0.5 / 0.7 / 1.0 between the model and a baseline) and the variant above were chosen on the same cutoffs, so 15.9% is somewhat optimistic; the winner was weight 1.0, i.e. the model alone for ordinary SKUs. The 2025-09-15 cutoff covers the Diwali window and gains only about 6% there (MAE 20.1 vs 21.4), because at that cutoff only one earlier Diwali exists in training.

## 7. Worst SKUs, and rare / new / promo / Diwali handling
Worst by WAPE in the backtest: `ELE-1006` (1.19), `GRP-1043` (1.09), `BRK-1088` (1.04) and `ELE-1031` (0.93). They sell about 0.5-0.8 units a week with 38-60% zero weeks, so the error is Poisson noise that no model can remove. `OIL-1004` and `ELE-1019` (about 0.39) sell about 11 units a week with no zero weeks but high week-to-week variance.
- **Rare SKUs** (more than 35% zero weeks in the last 52, `is_rare`, line 182): half a TSB/Croston-style demand rate (`tsb_rate`, line 61) and half the model (`blend`, line 220).
- **New SKUs** (`BRK-1105`, `CHN-1006`, 6 weeks of history): a blend of their own mean and their category's recent level, weighted by weeks observed (`special_forecast`, line 173). The forecast is flat, which is deliberate with 6 data points.
- Forecasts are clipped at 0 and written to 3 decimals; the file has exactly 160 rows.

## 8. Weakest part and what two more days would add
Weakest: **retrieval and the injection filter are hand-built heuristics** (synonym list, regex patterns) that fit this catalogue but would need maintenance on a new one; and the forecast has only two Diwali observations to learn from. Two more days: (1) a dense re-ranker behind the same fitment filter plus an offline retrieval evaluation set of about 100 labelled dealer queries; (2) a classifier-based injection detector and an LLM-judge pass on replies; (3) quantile forecasts so reorder points use real demand uncertainty instead of the 12-week σ; (4) a nightly retraining job instead of a committed CSV.
